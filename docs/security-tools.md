# Security Tools and Triage Process

## Назначение

В проекте используются три взаимодополняющих security-инструмента:

| Инструмент | Категория | Объект анализа |
|---|---|---|
| Bandit | SAST | Собственный Python-код |
| Gitleaks | Secret scanning | Рабочее дерево и Git-история репозитория |
| pip-audit | SCA | Прямые и транзитивные Python-зависимости |

Эти инструменты решают разные задачи и не заменяют друг друга:

- Bandit не предназначен для поиска секретов или CVE в библиотеках;
- Gitleaks не анализирует безопасность бизнес-логики приложения;
- `pip-audit` не проверяет собственный исходный код;
- автоматические scanners не заменяют ручной code review и threat modeling.

Все проверки встроены в GitHub Actions workflow и запускаются до публикации Docker image и deployment в staging-среду.

## Bandit — SAST

### Что проверяет Bandit

Bandit выполняет Static Application Security Testing: анализирует Python-код без запуска приложения.

Инструмент ищет потенциально небезопасные паттерны, включая:

- использование `eval()` и похожих динамических вызовов;
- небезопасную десериализацию;
- потенциально опасное использование `subprocess`;
- слабые криптографические алгоритмы;
- hardcoded password patterns;
- другие известные рискованные конструкции Python.

### Запуск в CI

В GitHub Actions Bandit запускается командой:

```bash
python -m bandit -r app -f json -o reports/bandit-report.json
```

Инструмент проверяет весь каталог:

```text
app/
```

Результат сохраняется в JSON-файл:

```text
reports/bandit-report.json
```

После завершения workflow этот файл доступен в GitHub Actions artifact:

```text
security-reports
```

### Локальный запуск

```bash
python -m bandit -r app -f json -o reports/bandit-report.json
```

Для читаемого вывода в Terminal:

```bash
python -m bandit -r app
```

### Как обрабатывать находку Bandit

1. Определить точное место находки и правило Bandit.
2. Проверить, при каких условиях вызывается код.
3. Оценить, контролируется ли входное значение пользователем или внешней системой.
4. Исправить код безопасной альтернативой, если риск подтверждён.
5. Повторно запустить тесты и Bandit.
6. Если находка признана false positive, зафиксировать обоснование в Pull Request или issue.

Suppression через настройки Bandit или комментарии в коде допустимы только после контекстной проверки и вместе с пояснением причины. Нельзя отключать finding только ради зелёного workflow.

### Демонстрация блокировки pipeline

Для проверки политики блокировки была создана отдельная учебная ветка:

```text
demo/bandit-failure
```

В ней использовался изолированный пример с `eval()`.

Bandit обнаружил паттерн `B307` и завершил workflow с ошибкой. Это демонстрирует, что security scan не является информационным: найденная проблема блокирует дальнейшие этапы CI/CD.

Небезопасный учебный файл не был merged в `main`.

## Gitleaks — Secret Scanning

### Что проверяет Gitleaks

Gitleaks ищет потенциально чувствительные данные, например:

- API keys;
- access tokens;
- passwords;
- private keys;
- cloud credentials;
- database connection strings;
- другие значения, соответствующие известным шаблонам секретов.

### Проверка Git-истории

В GitHub Actions checkout настроен с полной Git-историей:

```yaml
fetch-depth: 0
```

Поэтому Gitleaks получает доступ не только к текущим файлам, но и к предыдущим commit.

Это важно, потому что секрет может быть удалён из актуальной версии файла, но остаться в Git-истории и быть доступным через старый commit.

### Запуск в CI

В GitHub Actions Gitleaks устанавливается и запускается командой:

```bash
gitleaks detect \
  --source . \
  --report-format json \
  --report-path reports/gitleaks-report.json \
  --exit-code 1
```

Параметр:

```text
--exit-code 1
```

заставляет шаг завершиться ошибкой, если Gitleaks обнаруживает потенциальный секрет.

JSON-отчёт сохраняется в:

```text
reports/gitleaks-report.json
```

### Локальный запуск

```bash
gitleaks detect \
  --source . \
  --report-format json \
  --report-path reports/gitleaks-report.json
```

### Как действовать при находке

1. Немедленно удалить секрет из рабочего кода и конфигурационных файлов.
2. Считать секрет скомпрометированным.
3. Отозвать или ротировать значение у соответствующего провайдера.
4. Перенести новое значение в безопасное хранилище, например GitHub Actions Secrets.
5. Проверить Git-историю.
6. Повторно запустить Gitleaks и убедиться, что проблема устранена.

Удаление секрета только из последнего commit недостаточно: значение может оставаться в более ранней Git-истории.

В учебных демонстрациях допустимо использовать только искусственные тестовые значения. Рабочие ключи, токены, реальные пароли и private keys не должны использоваться для демонстрации.

## pip-audit — SCA

### Что проверяет pip-audit

`pip-audit` относится к Software Composition Analysis.

Инструмент сопоставляет версии Python-зависимостей с базами известных vulnerabilities и advisory. Проверяются:

- прямые зависимости из `requirements.txt`;
- транзитивные зависимости, устанавливаемые вместе с ними.

### Запуск в CI

```bash
python -m pip_audit \
  -r requirements.txt \
  -f json \
  -o reports/pip-audit-report.json
```

JSON-отчёт сохраняется в:

```text
reports/pip-audit-report.json
```

Если инструмент находит известную уязвимость, команда завершается с ошибкой и workflow становится красным.

### Локальный запуск

```bash
python -m pip_audit -r requirements.txt
```

Для сохранения JSON-отчёта:

```bash
python -m pip_audit \
  -r requirements.txt \
  -f json \
  -o reports/pip-audit-report.json
```

### Как действовать при находке

1. Определить затронутый пакет, установленную версию и advisory.
2. Проверить наличие исправленной версии.
3. Обновить зависимость в `requirements.txt`.
4. Повторно установить зависимости.
5. Запустить tests, `pip-audit` и Docker build.
6. Проверить совместимость обновлённой зависимости с приложением.

Наличие CVE не означает, что уязвимость автоматически эксплуатируема в конкретном приложении. Необходимо учитывать контекст:

- используется ли уязвимая функция;
- доступна ли она внешнему пользователю;
- есть ли компенсирующие меры;
- доступно ли обновление без нарушения совместимости.

## Security reports

В процессе CI создаются три JSON-отчёта:

```text
reports/bandit-report.json
reports/gitleaks-report.json
reports/pip-audit-report.json
```

Они не коммитятся в Git, потому что каталог `reports/` исключён через `.gitignore`.

После workflow GitHub Actions публикует доступные отчёты как artifact:

```text
security-reports
```

Для загрузки используется:

```yaml
if: always()
```

Поэтому artifact загружается даже при падении workflow, если хотя бы часть отчётов уже была сформирована.

## Упрощённая политика версии v1

Для учебного проекта применяется строгая политика блокировки:

| Инструмент | Условие блокировки |
|---|---|
| pytest | Упал хотя бы один тест |
| Bandit | Найдена проблема согласно текущей конфигурации |
| Gitleaks | Найден потенциальный секрет |
| pip-audit | Найдена известная уязвимость зависимости |
| Docker build | Docker image не собирается |

Если CI job не проходит, image не публикуется в GitHub Container Registry и deployment на staging VPS не запускается.

В production-среде пороги блокировки, severity thresholds, сроки исправления и процесс исключений обычно зависят от CVSS, эксплуатируемости, критичности сервиса, доступности исправления и утверждённого процесса risk acceptance.
