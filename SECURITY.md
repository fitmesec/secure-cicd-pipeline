# Security Policy

## Supported Version

Репозиторий является учебным DevSecOps-проектом.

Поддерживается текущая версия кода в ветке `main`. Она проходит automated tests, security checks, Docker image build, публикацию image в GitHub Container Registry и deployment в staging-среду.

---

## Reporting a Security Issue

Если вы обнаружили потенциальную security-проблему в этом репозитории:

1. Не публикуйте рабочий exploit, настоящий секрет, приватный ключ, пароль, токен или персональные данные в публичном GitHub Issue.
2. Создайте Issue с минимальным безопасным описанием проблемы.
3. Укажите:
   - краткое описание проблемы;
   - затронутый файл, компонент или workflow;
   - потенциальное влияние;
   - безопасные шаги воспроизведения;
   - возможный способ исправления, если он известен.
4. Не включайте в Issue чувствительные значения или команды, которые могут раскрыть секреты.

Для учебного проекта допустимо использовать только искусственные тестовые значения в демонстрациях security scanning.

## Handling Exposed Secrets

Если секрет случайно был добавлен в исходный код, Git-репозиторий или Git-историю:

1. Считайте секрет скомпрометированным.
2. Немедленно удалите его из рабочего кода и конфигурационных файлов.
3. Отзовите или ротируйте значение у соответствующего провайдера.
4. Перенесите новое значение в безопасное хранилище:
   - переменные окружения для локальной разработки;
   - GitHub Actions Secrets для CI/CD;
   - специализированное secret management solution в production-среде.
5. Проверьте Git-историю и повторно запустите Gitleaks.
6. Убедитесь, что секрет не отображается в workflow logs, screenshots, README, Issues или Pull Requests.

Удаления секрета только из последнего commit недостаточно: значение может оставаться доступным в предыдущих commit Git-истории.

## CI/CD Secrets

Для автоматического deployment в staging-среду GitHub Actions использует repository secrets.

К секретам относятся:

- адрес staging VPS;
- пользователь deployment;
- SSH private key;
- параметры SSH-подключения;
- токен доступа к container registry при необходимости.

Значения secrets:

- не хранятся в Git;
- не добавляются в `.env.example`;
- не публикуются в README;
- не должны попадать в screenshots или GitHub Actions logs.

Deployment выполняется отдельным непривилегированным пользователем `deploy` через SSH key authentication.

## Automated Security Checks

В GitHub Actions workflow выполняются следующие проверки:

| Проверка | Назначение |
|---|---|
| `pytest` | Проверяет ожидаемое поведение приложения |
| Bandit | Выполняет SAST-анализ Python-кода |
| Gitleaks | Ищет потенциально раскрытые секреты в файлах и Git-истории |
| `pip-audit` | Проверяет Python-зависимости на известные уязвимости |
| Docker build | Проверяет воспроизводимую сборку Docker image |
| Docker health-check | Проверяет готовность контейнера после deployment |
| External smoke test | Проверяет доступность staging endpoint `/health` извне |

Если обязательный этап завершается ошибкой, workflow становится красным.

Для `push` в `main` публикация Docker image и deployment запускаются только после успешного завершения CI job.

## Handling Security Findings

### Bandit finding

1. Проверить правило, место находки и контекст кода.
2. Определить, контролируется ли входное значение пользователем.
3. Исправить потенциально небезопасную конструкцию.
4. Повторно запустить tests и Bandit.
5. Если finding является false positive, зафиксировать обоснование в Pull Request или Issue.

Suppression через настройки инструмента или комментарии в коде допустимы только вместе с понятным пояснением причины.

### Gitleaks finding

1. Удалить секрет из кода.
2. Отозвать или ротировать его.
3. Перенести новое значение в GitHub Actions Secrets или другое безопасное хранилище.
4. Проверить Git-историю.
5. Повторно запустить Gitleaks.

### pip-audit finding

1. Проверить затронутый пакет, версию и advisory.
2. Определить наличие исправленной версии.
3. Обновить зависимость.
4. Запустить tests, `pip-audit` и Docker build.
5. Проверить совместимость обновлённой зависимости с приложением.

## Scope and Limitations

Deployment выполняется только в изолированную staging-среду и не предназначен для production-развёртывания.

Автоматические scanners помогают выявлять типовые риски, но не заменяют:

- ручной code review;
- threat modeling;
- архитектурный review;
- оценку бизнес-рисков;
- контекстный анализ security findings;
- полноценное управление security-инцидентами.

Дополнительные security-улучшения, включая container image scanning, DAST, SBOM, image signing и policy as code, описаны в roadmap проекта.
